# Распознавание сцен в видео тандемных парашютных прыжков

**Дата:** 2026-08-12
**Статус:** дизайн согласован, готов к планированию реализации
**Итерация:** 1 из 2 (качество; удешевление вынесено во вторую фазу)

## 1. Задача

Автоматически находить в видеозаписях тандемных прыжков пять типов сцен и выдавать их таймкоды в JSON. Монтаж, сборка ролика и любая работа с изображением в скоуп не входят — система только размечает время.

Целевые сцены:

1. **Интервью** — клиент говорит на камеру, на земле или в самолёте.
2. **Отделение** — момент покидания борта.
3. **Яркие моменты свободного падения** — пять подкатегорий: яркие эмоции, яркая жестикуляция, общий план, общий план с манёврами тандемной пары, облёт пары оператором.
4. **Раскрытие парашюта** — раскрытие купола тандемной пары.
5. **Приземление** — касание земли тандемной парой.

### Границы скоупа

Первая итерация оптимизируется по качеству, а не по стоимости. Промышленное решение с максимальной пропускной способностью — отдельная вторая фаза, которая будет опираться на метрики и эталонный набор, созданные здесь.

Не входит в первую итерацию: автоматический монтаж, синхронизация с музыкой, цветокоррекция, распознавание личности клиента, работа в реальном времени.

## 2. Входные данные

### Конфигурации съёмки

Основной режим — **одна камера внешнего оператора**. Камера на руке инструктора присутствует реже и рассматривается как опциональный дополнительный источник.

| Конфигурация | Частота | Последствия |
|---|---|---|
| Только оператор | основная | Телеметрия описывает оператора, а не тандем |
| Оператор + рука инструктора | реже | Телеметрия тандема доступна, эмоции крупным планом надёжнее |
| Только рука инструктора | редко | Общий план и облёт недоступны |

### Файлы

Оригинальные записи с камер GoPro/DJI, без перекодирования, с сохранённым потоком телеметрии GPMF.

Длинные записи разбиваются камерой на чанки по 4 ГБ (`GX010123.MP4`, `GX020123.MP4`, …). Один прыжок — это набор чанков, который система обязана собрать в одну логическую запись по номеру сессии в имени файла и по непрерывности временных меток.

### Что даёт телеметрия

Поток GPMF содержит акселерометр, гироскоп, GPS с абсолютной меткой времени UTC и, на части моделей, барометрическую высоту.

**Критично:** в основном режиме телеметрия принадлежит оператору, а оператор живёт по собственному профилю полёта. Он раскрывается ниже и позже тандема и приземляется раньше него. Поэтому пик перегрузки в его акселерометре — это **его** раскрытие, а не раскрытие снимаемой пары. Использовать события телеметрии оператора как события тандема — ошибка, дающая уверенный, но неверный таймкод.

Надёжно переносятся с оператора на тандем только отделение (борт покидают почти одновременно) и границы фазы свободного падения.

## 3. Выходные данные

Один JSON на прыжок.

```json
{
  "jump_id": "2026-08-12_001",
  "schema_version": 1,
  "t0_utc": "2026-08-12T09:14:03.250Z",
  "sources": [
    {
      "role": "operator",
      "files": ["GX010123.MP4", "GX020123.MP4"],
      "offset_s": 0.0,
      "duration_s": 512.3,
      "has_telemetry": true
    }
  ],
  "degradations": [
    {"code": "NO_INSTRUCTOR_CAM", "severity": "info",
     "message": "Камера инструктора отсутствует; эмоции детектируются только с камеры оператора"}
  ],
  "phases": [
    {"type": "ground_pre", "start": 0.0, "end": 245.0, "source": "telemetry", "confidence": 0.99}
  ],
  "events": [
    {"type": "exit", "t": 245.6, "source": "telemetry", "confidence": 0.97},
    {"type": "canopy_open", "t": 312.4, "source": "visual", "confidence": 0.71}
  ],
  "scenes": [
    {"type": "interview", "start": 12.0, "end": 48.5, "source": "fusion", "confidence": 0.88}
  ],
  "highlights": [
    {
      "rank": 1, "subtype": "emotion", "start": 268.2, "end": 272.6, "score": 0.91,
      "camera": "operator",
      "features": {"face_area_frac": 0.18, "blob_area_frac": 0.31}
    }
  ]
}
```

Ключевые решения по формату.

**Все времена — в секундах от `t0_utc`, а не от начала файла.** Файлы разных камер начинаются в разные моменты; `offset_s` у каждого источника позволяет перевести время прыжка в позицию внутри конкретного файла. Это делает JSON пригодным для нарезки любой из дорожек.

**Поле `source` обязательно у каждого результата** и принимает значения `telemetry`, `visual` или `fusion`. По нему потребитель отличает таймкод, за который система ручается физикой, от таймкода, предположенного по картинке. Без этого различия уверенность в 0.7 от датчика и от нейросети выглядят одинаково, хотя стоят разного доверия.

**Яркие моменты — ранжированный список кандидатов, а не найденные факты.** Событий раскрытия ровно одно, ярких моментов может быть три или тридцать. Правильное поведение — отдать отсортированный список и позволить потребителю обрезать его по своему порогу.

**`degradations` — часть контракта, а не логи.** Любое ухудшение условий работы фиксируется явно.

## 4. Архитектура

Три стадии, разделённые артефактами на диске.

```
видео ──[стадия 1: извлечение]──> артефакты ──[стадия 2: анализ]──> scenes.json
                  GPU                 диск            CPU
                один раз                            секунды
                                                        │
                            эталонная разметка ──[стадия 3: оценка]──> метрики
```

### Стадия 1 — извлечение признаков

Единственный проход по видео. Читаются только опорные кадры (`-skip_frame nokey`), что на порядок дешевле полного декодирования. Контроль резкости не нужен — все кадры экшн-камер достаточно чёткие, — поэтому полное разрешение не требуется ни на одном шаге.

Артефакты на прыжок:

- `telemetry.parquet` — сенсоры, приведённые к шкале UTC
- `frames/*.jpg` — опорные кадры, 720p
- `features.parquet` — построчно на кадр: эмбеддинг, геометрия контрастного пятна, наличие и площадь лица, положение кистей рук, оптический поток

Разрешение 720p выбрано осознанно: энкодеры принимают 224×224, но при 480p тандемная пара на общем плане доходит до входа сети в виде тридцати пикселей, а при 720p — полусотни. Разница в стоимости хранения незначительна.

Оценка объёма для 300 прыжков: около 43 ГБ кадров и менее 1 ГБ признаков. После этой стадии исходное видео не требуется до финальной нарезки.

### Стадия 2 — анализ

Не касается видео вообще. Читает артефакты, выдаёт JSON. Считается секунды, поэтому цикл подкрутки логики измеряется секундами, а не часами. Это же разделение изолирует вторую фазу проекта: удешевление затронет только стадию 1.

### Стадия 3 — оценка

Сравнивает выход с эталонной ручной разметкой, считает метрики.

### Синхронизация источников

Обе камеры приводятся к абсолютной шкале UTC по GPS-меткам из GPMF. Событийная синхронизация здесь неприменима: профили полёта оператора и инструктора не совпадают, общих событий в телеметрии у них нет.

## 5. Компоненты

### 5.1 Физический детектор фаз

Работает по сигнатурам в телеметрии. Существенная деталь: акселерометр измеряет собственное ускорение, поэтому в установившемся свободном падении показывает около 1g — сопротивление воздуха уравновешивает вес. Невесомость наблюдается только в первые секунды после отделения.

| Фаза / событие | Сигнатура |
|---|---|
| На земле | Высота постоянна, вектор ускорения стабильно ≈1g |
| Набор высоты | Монотонный рост высоты, 3–5 м/с, порядка 15–20 минут |
| Отделение | Провал \|a\| почти до нуля с возвратом к 1g примерно за 10 с; вертикальная скорость разгоняется до ~55 м/с |
| Свободное падение | Вертикальная скорость 45–60 м/с, \|a\| около 1g с высоким шумом |
| Раскрытие *(оператора)* | Пик 2–4g длительностью 2–4 с, затем падение вертикальной скорости до 5–7 м/с |
| Под куполом | Вертикальная скорость 4–7 м/с, устойчиво |
| Приземление *(оператора)* | Высота площадки, ударный всплеск, скорость к нулю |

Поверх детектора работает конечный автомат, требующий физически обязательного порядка фаз. Его задача — не находить события, а отбраковывать бессмыслицу: раскрытие не может предшествовать отделению. Нарушение порядка означает сбой телеметрии и записывается в `degradations`.

В основном режиме съёмки из этой таблицы используются только строки до свободного падения включительно — раскрытие и приземление оператора к тандему отношения не имеют.

### 5.2 Сегментация тандемной пары

В небе пара — единственный контрастный объект в кадре, поэтому её локализация не требует детектора объектов: достаточно порога по контрасту и связных компонент. Стоимость — микросекунды на кадр.

Геометрия пятна несёт основную информацию с камеры оператора:

- площадь — дистанция до пары
- производная площади — сближение или отход
- траектория центра в сочетании со смещением фона — облёт
- вытянутость и угол главной оси — ориентация пары
- число компонент — раздельные фигуры против единой группы

**Площадь пятна работает переключателем режима детекции.** Пятно крупное — оператор рядом, включаются лицо, эмоции, жесты. Пятно мелкое — оператор отошёл, работают композиция, манёвры, облёт. Один дешёвый признак вместо ветвления по типу камеры.

**Допущение, требующее проверки на данных:** метод предполагает небо в качестве фона. Когда оператор идёт выше пары и снимает вниз, фон становится земляным и сегментация может деградировать. Доля таких кадров измеряется на эталонном наборе; при существенной доле включается запасной путь через эмбеддинги.

### 5.3 Визуальные детекторы событий

Обязательны уже в первой итерации, поскольку в основном режиме телеметрия этих событий не даёт.

**Раскрытие тандема.** Выражено ярко: площадь пятна скачком вырастает в разы, форма меняется на куполообразную, относительное движение резко замедляется.

**Приземление тандема.** Сложнее: оператор к этому моменту обычно уже на земле и снимает заход с земли, фон пёстрый, контрастная сегментация неприменима. Здесь работает семантика кадра по эмбеддингам.

### 5.4 Интервью

Определяется пересечением трёх условий: фаза на земле или в самолёте, речь в звуковой дорожке, лицо в кадре при малом движении камеры.

Детектор голосовой активности — самый сильный признак из имеющихся и практически бесплатный на процессоре. Он отсекает подавляющее большинство ложных срабатываний ещё до анализа изображения.

### 5.5 Яркие моменты

| Подкатегория | Ведущий признак |
|---|---|
| Яркие эмоции | Лицо крупно + классификатор выражения по кропу |
| Яркая жестикуляция | Положение кистей рук относительно тела |
| Общий план | Площадь и центрированность пятна в среднем диапазоне |
| Манёвры пары | Циклическое изменение вытянутости и угла главной оси пятна |
| Облёт оператором | Пятно удерживается в кадре при смещении фона — паралакс |

Признаки сводятся в единый вектор на момент времени, поверх которого обученная голова выдаёт оценку по каждой подкатегории.

Гироскоп инструктора для манёвров **не используется** — камеры на руке в большинстве прыжков нет.

### 5.6 Временная сборка

Покадровые решения дрожат. Финальный шаг: сглаживание оценок по времени, гистерезис с разными порогами на вход и выход из сегмента, отбрасывание фрагментов короче минимальной длительности, непригодной для монтажа.

## 6. Обучение

Разделение труда между физикой и обучением — центральная идея дизайна: разметка тратится только на то, что действительно требует человеческого суждения.

**Автоматическая разметка.** Телеметрия способна размечать события без участия человека, но объём такой разметки ограничен сильнее, чем кажется, и это стоит зафиксировать честно.

Отделение и границы свободного падения размечаются автоматически на **всём** архиве: эти события переносятся с оператора на тандем без искажения.

Раскрытие и приземление тандема размечаются автоматически только там, где одновременно присутствуют обе камеры: телеметрия инструктора даёт время события, камера оператора даёт соответствующую картинку. Поскольку камера на руке встречается реже, такое пересечение — меньшинство архива. При сотнях прыжков это всё равно даёт десятки размеченных примеров, чего для обучения лёгкой головы поверх замороженных эмбеддингов достаточно, но говорить о наборе промышленного размера здесь нельзя.

**Следствие для рисков:** визуальный детектор приземления тандема — самое слабое место дизайна. Он нужен в основном режиме, работает по семантике на пёстром земляном фоне и обучается на наименьшем количестве примеров. Если какая-то часть системы не выйдет на целевую метрику, вероятнее всего это будет он. Объём доступных для него примеров измеряется на архиве в первую очередь; при нехватке добирается ручной разметкой.

**Ручная разметка.** Требуется только для ярких моментов. Один класс вместо пяти.

**Обучаемая часть.** Лёгкая голова поверх замороженных эмбеддингов — логистическая регрессия или неглубокая временная модель. Считается минуты на процессоре. Дообучение самого энкодера в первой итерации не планируется; вопрос пересматривается по результатам метрик.

**Стоимость.** Вычисления дёшевы, дорого перемещение данных: архив в 300 прыжков — порядка 6 ТБ, заливка которых занимает недели, тогда как обработка стоит доллары. Поэтому видео не покидает машину, где лежит; наружу выходят только эмбеддинги, укладывающиеся в сотни мегабайт. Аренда облачного GPU (RunPod от $0.34/час, Vast.ai от $0.13/час) рассматривается только если по итогам метрик потребуется дообучение энкодера — это несколько часов аренды.

## 7. Деградация и отказы

Система обязана признавать ухудшение условий явно. Тихая выдача правдоподобного числа — худший исход, поскольку ошибка всплывёт уже в смонтированном ролике у клиента.

| Код | Условие | Реакция |
|---|---|---|
| `NO_TELEMETRY` | Поток GPMF отсутствует или повреждён | Фазы только визуально, уверенность снижена |
| `NO_INSTRUCTOR_CAM` | Камера на руке отсутствует | Раскрытие и приземление только визуально |
| `PHASE_ORDER_VIOLATION` | Конечный автомат не сошёлся | Фазы помечены ненадёжными |
| `SYNC_FAILED` | GPS-метки не пересекаются | Источники обрабатываются независимо |
| `GROUND_BACKGROUND` | Доля кадров с земляным фоном выше порога | Сегментация пятна отключена, работают эмбеддинги |
| `CHUNK_GAP` | Разрыв между чанками записи | Разрыв отражён в `sources`, времена скорректированы |

## 8. Валидация

**Эталонный набор:** 15–20 прыжков с ручной разметкой всех пяти сцен, отобранных так, чтобы покрыть обе конфигурации съёмки, разную погоду и разное время суток. Разбиение на калибровочную и отложенную части; пороги настраиваются только на калибровочной.

**Метрики.**

- Событийные сцены (отделение, раскрытие, приземление): доля попаданий в допуск **±0.5 с** по времени.
- Интервью: пересечение по времени с эталонным интервалом (IoU).
- Яркие моменты: точность в первой десятке кандидатов, поскольку монтажёр просматривает верхушку списка, а не хвост.

Эти цифры становятся порогом приёмки для второй итерации. Без зафиксированного эталона разговор о «приемлемом качестве» при удешевлении будет беспредметным — это и есть главная причина, по которой валидация входит в первую итерацию, а не откладывается.

## 9. Допущения, проверяемые на реальных данных

Каждый пункт — риск, способный изменить дизайн. Проверяются в первую очередь, до написания детекторов.

1. GPS-метка UTC реально присутствует в файлах обеих камер.
2. Интервал между опорными кадрами у используемых камер — он задаёт временное разрешение всей системы.
3. Доля кадров свободного падения с земляным фоном.
4. Раскрытие тандема действительно попадает в кадр оператора.
5. Конвенция именования и разбиения на чанки в архиве.
6. Насколько близко оператор реально подходит к паре — от этого зависит применимость детектора эмоций в основном режиме.
7. Доля прыжков, где присутствуют **обе** камеры одновременно — она определяет объём автоматической разметки для визуальных детекторов раскрытия и приземления (раздел 6).
8. Как выглядит приземление тандема в кадре оператора: снимается ли оно вообще, с земли или с воздуха, попадает ли момент касания в кадр.

## 10. Бэклог

**Приложение для ручной проверки качества нарезки.** Принимает на вход `scenes.json` и папку с исходными файлами, нарезает клипы по указанным сегментам и складывает их в выходную папку. Поддерживает фильтрацию по типу сцены, подкатегории, порогу оценки и длительности, а также отбор первых N кандидатов. Имена выходных файлов несут ранг, подкатегорию и оценку, чтобы результат читался без открытия JSON. Дополнительно формирует HTML-страницу с превью для быстрого просмотра всей выдачи разом.

Инструмент нужен не только для проверки: он же ускоряет создание эталонной разметки, поскольку позволяет просматривать кандидатов пачками вместо перемотки исходников.

**Вторая фаза — промышленное решение.** Максимальная пропускная способность при минимальной стоимости и приемлемом качестве по метрикам раздела 8. Затрагивает только стадию 1: замена тяжёлых моделей дистиллированными, отказ от телеметрии там, где визуальные детекторы уже обучены, пакетная обработка, очередь задач.

**Прочее.** Определение роли камеры автоматически, без опоры на имена файлов. Обработка прыжков с несколькими операторами. Оценка качества самого кадра для отбора лучшего из нескольких похожих моментов.
